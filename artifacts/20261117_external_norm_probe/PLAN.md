# External norm judgment with positive and negative cases

This is a frozen-model, external-data probe, separate from the ongoing learned relation-policy experiment. It tests whether a local language model can distinguish appropriate from inappropriate information flows without being rewarded for refusing everything. It does not execute business tools, measure task utility, establish natural norms independently, or demonstrate transfer of the trained135Mpolicy.

Use author-published CAMBER PrivacyLens+ at pinned revision62e5d4529d291ff0eb1f8f9565f035e8a8827589, underCC-BY4.0. Restrict to `no_expansion` rows; exclude all label-dependent, reasoning-guided and label-independent expanded narratives. These base positive examples are still synthetic modifications of the original negative examples and may change subjects or data types. They are not consent-only or task-equivalent interventions. Public-data pretraining contamination is unknown.

Cross-check all493negative base seeds against the earlier pinned PrivacyLens dataset:492match exactly;1differs and is excluded before sampling, with differences retained in SOURCE_MATCH_AUDIT.json. Sample16different non-crowd source-title groups, one original seed each, using seed31117; retain its appropriate/inappropriate versions. This gives32semanticcases,16positive and16negative. Two option orders per case yield64requests. Title grouping does not prove source-document independence or eliminate semantic overlap.

Only the five scenario fields and neutral decision instructions enter the prompt. IDs, original names, expansion metadata, source titles and labels stay outside model input. The model may answer undetermined when context is insufficient. Audit reports unresolved counts separately; no forced binary or legal-action decoder. Free outputs are sealed before scoring against author labels. Source labels are a benchmark reference, not a legal/business judgment made by this project.

Pinned local Qwen2.5:7B Q4 model digest,temperature0,seed17,CPU4threads,2048context,12newtokens. No fine-tuning, no optimizer updates, no prompt retries.25sclient I/O timeout and completed-response wall-time acceptance limit,60swarmup I/O timeout; these are not a hard kill deadline for the server. Stop and retain failure on the first request error or over-limit completion. Run after the CPU training/evaluation worker finishes to avoid contention. If a user-loaded Ollama model is present, leave it untouched and defer the probe. A single empty warmup is recorded as a loading operation, not a scored request. Unload only the run's own model and record the subsequent `/api/ps` state; an unload request alone is not proof of release.

Report per-class label agreement, abstention, both-order agreement, paired positive/negative robustness, and always-share/always-withhold/always-undetermined baselines. Do not promote this selected diagnostic to an official CAMBER reproduction or complete external safety/utility validation.

Before the first request, SCORING_PLAN.json freezes both strict whole-response parsing (primary) and a unique explicit ANSWER-letter extraction allowing extra explanation (secondary). Both are reported, including unresolved and invalid counts. The second metric distinguishes formatting failure from decision disagreement; it must not replace the primary after outcomes are seen. Runtime pins the scorer hash as well as data and worker hashes.
